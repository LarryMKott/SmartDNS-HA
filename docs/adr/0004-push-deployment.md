# ADR-0004：控制机 SSH 推送 + 节点本地脚本

- 状态：已接受
- 日期：2026-10-21
- 相关：[deployment.md](../deployment.md)

## 背景

部署需要同时操作两台节点：装服务、写 keepalived、配同步、验证。可选方式：在节点上运行常驻 Agent 拉取指令（pull）、用 Ansible 等配置管理工具推送、或从控制机用 SSH 直接执行（push）。

## 决策

采用 **push 模型**：

1. `deploy_dns.sh` 在控制机执行，先 `scp -r ./* root@node:/opt/dnsha/`。
2. 然后按固定顺序远程调用节点上的 `install_dns.sh`、`keepalived_config.sh`、`sync_config.sh`、`verify_deploy.sh`。
3. 每个节点脚本都可以脱离控制机单独执行，参数齐全。
4. 控制机只负责编排与日志，不保存集群状态。

## 后果

**正面**

- 节点上不需要常驻 Agent，故障面小。
- 分步部署与一键部署共用同一批脚本，排障时可以在节点上重放单步。
- 控制机可以是运维笔记本、跳板机，不进入高可用范围。

**负面**

- 控制机是**变更单点**：它不可用时无法部署/修复（但不影响 DNS 服务）。
- 部署是串行的，中途失败会留下"部分节点已更新"的状态；依赖脚本幂等 + 人工从失败步骤继续。
- 需要控制机到节点的 root SSH；密码方式会暴露在命令行。
- 最后一步 `verify_deploy.sh` 失败只告警（历史行为），退出码不可靠，必须额外巡检。

## 备选方案

| 方案 | 放弃原因 |
| --- | --- |
| 节点常驻 Agent 拉取 | 多一个需要自身高可用与升级的组件；增加攻击面 |
| Ansible | 引入控制端依赖；仍要写同样的配置生成逻辑，收益主要是幂等与并发 |
| 云厂商自定义脚本/cloud-init | 绑定云平台，无法用于物理机/自建机房 |

## 证据

- `deploy_dns.sh` 的 7 个阶段与失败处理见 [architecture.md](../architecture.md#控制链路部署时)。
- `docs/deployment.md` 的分步部署与一键部署命令完全对应同一批脚本参数。
